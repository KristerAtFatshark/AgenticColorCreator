# Status

## General Status
- WPF desktop app scaffold is working with `AgenticColorCreator.App`, `AgenticColorCreator.Core`, and `AgenticColorCreator.Tests`.
- The app can create, load, edit, validate, and save `agentic_colors.md` markdown files.
- The main UI uses `Colors` and `UI Preview` tabs for editor work and themed control previewing.
- Shared theme resources live in `AgenticColorCreator.App\CFStyles\CFDarkStyles.xaml` and use explicit `CF.` brush keys plus keyed `CF...` styles/templates.
- Custom previewed controls currently include `CFTextBox`, `CFInt`, `CFFloat`, `CFSlider`, `CFColor`, `CFHdrColor`, `CFCheckBox`, `CFRadioButton`, `CFComboBox`, and `CFTreeView`.
- `CFListTreeView` is implemented as a recycling-virtualized ListView-backed tree with a persistent structural graph, `SourceItems` structure input, and non-rebuilding `MatchedItems` filter mask.
- `CFTextBox` now supports delayed external value commits plus immediate validation feedback while typing.
- `CFTextBox` now also commits valid pending edits immediately on focus loss, so tab-out and click-outside behave the same as Enter for textbox-based controls.
- `CFInt` now uses `CFTextBox` as its delayed-commit text layer and mixed-state implementation, applying actual integer validation through that shared control.
- `CFFloat` now uses `CFTextBox` as its delayed-commit text layer and mixed-state implementation, applying invariant float validation with configurable decimal-place limits.
- `CFSlider` now provides a reusable slider + editable numeric textbox control, with the textbox reusing `CFFloat` behavior so slider drags and manual numeric edits stay synchronized.
- `CFSlider` now calculates a deterministic fixed width for its embedded `CFFloat` editor based on the wider of the formatted `Minimum`/`Maximum` values plus the spinner/padding allowance, instead of relying on `Auto` width.
- `CFSlider` no longer exposes separate `SmallChange` and `LargeChange` host properties; it now uses the single exposed `Step` value for both slider paging and numeric editing because that is the only increment concept needed in this app.
- `CFSlider` now supports mixed state: the slider portion shows a `- Mixed -` overlay like `CFColor`, while the embedded `CFFloat` simply inherits the same `IsMixedState` binding so its existing mixed-state behavior is reused directly.
- When `CFSlider` enters mixed state, the actual `Slider` control is now collapsed underneath the overlay instead of remaining visible behind it, matching the `CFColor` pattern where the editable surface is hidden while mixed.
- The `CFSlider` preview mixed-state checkbox in `MainWindow` now sits on its own row so it is no longer overlapped by the title text and is clickable again.
- The `CFSlider` preview card now also includes a disabled `CFSlider` instance directly beneath the active one, matching the enabled/disabled preview pattern used by the other cards.
- The `CFSlider` preview card layout now uses a compact vertical settings form plus a wider `420px` preview card, which was necessary to keep the `CFFloat`/`CFInt` spinner buttons visible in the `MainWindow` preview without regressing slider usability.
- The shared slider template now restores clickable track paging and visible tick rendering, and `CFSlider` now surfaces `TickFrequency`, `TickPlacement`, `Ticks`, and `IsSnapToTickEnabled` so it preserves more of the stock WPF slider behavior.
- The slider template’s original visual proportions were restored after the track-click fix: the repeat-button visuals now keep their prior centered `Height` values while the hit area remains large enough for track paging.
- The slider template now collapses the tick rows completely when `TickPlacement=None`, so sliders without ticks stay vertically centered and do not reserve empty space above or below the track.
- The `CFSlider` preview no longer uses a temporary tick-placement dropdown; it now uses explicit buttons for `None`, `Bottom`, `Top`, and `Both`, avoiding the preview regression caused by the earlier enum-combobox experiment.
- The root grid of `CF.HorizontalSliderTemplate` is now vertically centered as well, so collapsing tick rows actually centers the no-ticks slider instead of leaving the content aligned to the top of the control slot.
- `CFColor` now provides a reusable color-well control with hex display, transparent checker preview, mouse-over border feedback, and picker-dialog integration.
- `CFHdrColor` now provides an HDR-aware color-well control that keeps hex `Value` plus a separate `Stops` double and uses HDR/SDR conversion helpers to preview and edit HDR-adjusted color output.
- `CFColor` and `CFHdrColor` mixed state now hide their text-entry fields behind a `- Mixed -` overlay while keeping the swatch/picker interactive; in mixed mode the picker starts from temporary opaque black and only exits mixed mode if the user picks a non-default black color.
- The `CFTreeView` preview now includes 200 deterministic randomized sample entries in addition to the original hand-picked nodes so large-item behavior can be tested directly in the `UI Preview` tab.
- The `UI Preview` treeview card now exposes the stress-entry count via a `CFInt` labeled `Stress Entry Count` (default `200`, bound to `MainWindowViewModel.PreviewTreeStressEntryCount`); changing it rebuilds `PreviewTreeViewNodes` so performance can be measured at arbitrary sizes.
- `CFTreeView` now scrolls the first externally selected item into view after `SelectedValues` changes, so preview actions like `Select Primary` also move the scrollbar to the correct position.
- `CFTreeView` performance was improved while keeping all nodes expanded by default: virtualization/recycling is enabled at the tree and item levels, and external selection updates now reuse the existing visual tree instead of rebuilding it.
- `CFTreeView` no longer exposes or previews a mixed-state mode; the control now behaves as a plain selectable tree without any `IsMixedState` surface or overlay.
- `CFTreeView` now exposes public `CollapseAll()` and `CollapseAllExceptSelectedItemParents()` helpers so hosts can quickly collapse the tree either fully or down to just the ancestor paths of the current selection.
- `CFTreeView` now exposes a `CollapseAllThresholdItemCount` int dependency property (default `100`); the decision is made from `NodesSource.Count` before any tree items are created, so when the source exceeds the threshold every generated item is built with `IsExpanded=false` instead of being expanded and then collapsed afterward. The `UI Preview` treeview card exposes this via a `CFInt` labeled `Collapse All Threshold`.
- `CFTreeView` build path was optimized to reduce initial UI lag on large sources: intermediate `TreeViewNode.Children` is now a `List<T>` with a per-node child-name `Dictionary` index (removes O(N^2) `FirstOrDefault` sibling scans), `BuildTreeViewNodes` uses a shared split-separator array plus `string.Concat` for path building (removes per-segment LINQ and interpolation allocations), selection collection is inlined during item creation (removes a second recursive walk), default DP values (`IsExpanded=false`, `IsSelected=false`, `IsMultiSelected=false`) are no longer set explicitly on new items, and the built root items are assigned as a batch via `TreeView.ItemsSource` so the WPF virtualizing panel can generate containers on demand instead of processing per-item `Items.Add` container generation.
- `CFTreeView` rebuilds are now split across threads: the source snapshot and the pure `BuildTreeViewNodes` step run on a background `Task.Run` thread, and only the `CFTreeViewItem` construction (which has DP thread-affinity) and the final `ItemsSource` assignment happen back on the UI dispatcher. A monotonically increasing rebuild generation token prevents an older background result from overwriting a newer one when the source changes rapidly.
- `CFTreeView` now exposes `BeginUpdate()` / `EndUpdate()` for callers that know their source updates are full-replace. All source-triggered rebuilds are suppressed between the outermost pair; a single rebuild is scheduled on `EndUpdate` if any were requested.
- `CFTreeView` now also auto-batches source `CollectionChanged` bursts internally: on the first change in a burst it opens a batch itself and closes it on the next `DispatcherPriority.Background` tick, so a typical `Clear` + N × `Add` sequence coalesces into exactly one rebuild without the host needing to call `BeginUpdate` / `EndUpdate` explicitly. Manual host calls still nest correctly through the same suppression counter.
- The `CFTreeViewControl` folder `README.md` was rewritten to match current behavior: `CollapseAllThresholdItemCount` DP, `BeginUpdate`/`EndUpdate` semantics, threaded rebuild pipeline with background node build and generation-token cancellation, automatic full-replace coalescing, virtualization notes, and updated icon fallback behavior.
- `CFTreeView` capacity pre-sizing no longer uses `Dictionary.EnsureCapacity` (which is .NET Core / .NET 5+ only); instead the `_treeViewItemsByValue` dictionary field is reassigned to a new dictionary constructed with the estimated capacity, keeping the same grow-avoidance benefit while staying compatible with older framework versions the control needs to support.
- `MainWindowViewModel.PreviewTreeViewNodes` is now a settable notify property backed by `SetProperty`; `RebuildPreviewTreeViewNodes` builds a plain `List<TreeViewSourceEntry>` first and then assigns a single freshly-constructed `ObservableCollection<TreeViewSourceEntry>` to the property. This mirrors the production usage pattern (source always arrives as a fully-populated `ObservableCollection`) and lets `CFTreeView` handle it via one `NodesSource` DP change instead of a `Clear + N × Add` burst.
- `MainWindowViewModel.AddPreviewTreeViewTail` and `RemovePreviewTreeViewTail` were rewritten in the same style: they build the new list, then swap `PreviewTreeViewNodes` to a new `ObservableCollection` wrapping that list.
- `CFTreeView` now raises a public `RebuildCompleted` event on the UI thread after each rebuild finishes (including the `NodesSource == null` clear path). Hosts and tests can subscribe to await the async rebuild pipeline before inspecting the visual tree.
- The `AgenticColorCreator.Tests` project was retargeted from `net8.0` to `net8.0-windows` with `<UseWPF>true</UseWPF>` and now references `AgenticColorCreator.App`, so WPF-dependent controls can be exercised in xUnit. `StartupPathTests.cs` gained an explicit `using System.IO;` because the WPF SDK's implicit-usings set does not include it.
- Added `AgenticColorCreator.Tests\CFTreeViewLoadPerformanceTests.cs` which populates a `CFTreeView` with 350 000 randomized entries on a dedicated STA thread, merges `CFDarkStyles.xaml` into the test-time `Application` resources, and pumps the dispatcher until the new `RebuildCompleted` event fires. It prints entry-generation and rebuild timings to the test output for perf comparison, and asserts the rebuild completes within a two-minute cap.
- Current 350 000-entry baseline recorded from that test on the local dev machine: entry generation ~440 ms, `CFTreeView` rebuild ~152 700 ms. The rebuild time is now dominated by UI-thread `CFTreeViewItem` construction (DP overhead per node), not by the off-thread `BuildTreeViewNodes` step, so future perf work should focus on the item-construction phase.
- `CFTreeView` now supports optional lazy child materialization via two new DPs: `EnableLazyChildMaterialization` (bool, default `false`) and `LazyChildMaterializationDepth` (int, default `2`). When enabled, subtrees at or below the configured depth are not built up front — a single sentinel object is inserted so WPF still renders the expand chevron, and real `CFTreeViewItem` children are materialized on first `Expanded` (the sentinel is swapped out and the handler unhooks itself). Deeper subtrees continue to defer recursively based on the parent-chain depth walked at expansion time. Lazy is automatically skipped when the current rebuild would not start collapsed (`CollapseAllThresholdItemCount` not exceeded), because there is no visible collapse state to defer work behind. Any ancestor of a value in `SelectedValues` is force-materialized so external selection still lands on a real item even under lazy mode.
- `CFTreeViewItem` gained internal `SourceNode` (backing reference to the `TreeViewNode`) and `HasLazyPlaceholder` fields used by the lazy materialization path.
- The `UI Preview` treeview settings row now exposes both lazy options: a `Lazy Materialization` checkbox and a `Lazy Depth` `CFInt`, bound to new `MainWindow` DPs `PreviewTreeViewLazyMaterializationEnabled` / `PreviewTreeViewLazyMaterializationDepth`.
- `CFTreeViewLoadPerformanceTests` was refactored into a shared `RunLoadScenario` helper and now runs two 350 000-entry scenarios: the existing eager path plus a new lazy-materialization scenario at depth `2` with auto-collapse active. Recorded local baseline for the lazy scenario: entry generation ~360 ms, `CFTreeView` rebuild ~41 800 ms (about a 3.6x reduction vs the eager baseline for the same source).
- Fixed two lazy-materialization defects: (1) the sentinel is now a `TreeViewItem` with `Visibility=Collapsed`/`Focusable=false`/`IsEnabled=false` instead of a raw `object`, so the deferred child no longer briefly renders as the string `System.Object` while the parent is expanded; (2) `MaterializeLazyChildren` now calls `CreateTreeViewItem` with `startCollapsed=true`, so materializing one parent only reveals its direct children instead of cascading the auto-expand + auto-materialize chain into deeper subtrees. Grandchildren remain deferred with their own sentinel until the user actually expands them.
- `CFTreeView` now exposes a public `SelectFirstItemAndFocus()` helper that selects the first root item, brings it into view, and focuses both the control and the item (focus is deferred to `DispatcherPriority.Loaded` so the container is realized first). Returns the selected `CFTreeViewItem` or `null` if the tree is empty. Uses the existing forced-selection-clear + `SelectSingleItem` code path in multi-select mode, so `SelectedValues` and `SelectedTreeViewItems` are updated the same way as a manual click. The `UI Preview` treeview card exposes this via a new `Select First + Focus` button wired to `MainWindow.OnSelectFirstTreeViewItemClick`.
- `CFTreeView` now commits the focused item as the current selection when the user presses `Enter` while keyboard-navigating with the arrow keys. The handler is wired via `PreviewKeyDown="OnPreviewTreeViewPreviewKeyDown"` on the inner `TreeView`, resolves the focused `CFTreeViewItem` from `Keyboard.FocusedElement` (walking ancestors if focus is on a child element), and commits through a new `CommitKeyboardSingleSelection` helper that leaves the item's `IsSelected` flag on (in addition to `IsMultiSelected` when applicable). Keeping `IsSelected = true` after keyboard commit fixed a regression where subsequent arrow-key presses jumped back to the first root instead of moving to the next sibling — the built-in WPF TreeView uses `IsSelected` as its arrow-navigation anchor, and the mouse-click path leaves it `false` on purpose. The CF item style already renders identical visuals for both flags so no other change was needed. `Ctrl+Enter` continues to toggle multi-selection via the existing `ToggleItemSelection` path.

The keyboard-commit path no longer calls `focusedItem.Focus()` after the selection change because the item is already focused and re-focusing during the built-in selection-change reentry can throw.

That runs after the framework's `TreeView.OnKeyDown` has already moved the focused item (or decided it cannot), so tree navigation still works everywhere it did before, but the event no longer bubbles up to the outer `ScrollViewer` on the preview page — previously, hitting `Down` on the last visible row (or `Up` on the first) scrolled the whole preview page instead of staying inside the tree.

## Active Issues
- Rebuilding the full debug solution can fail while another process is locking `AgenticColorCreator.Core.dll`.
- Broad WPF test runs can exceed two minutes because the existing 350,000-entry tree performance tests are expensive and current command-line exclusion filters did not prevent the wait; focused `CFWindowTests` pass.
- The refactored `CFTextBox`, `CFInt`, `CFFloat`, `CFColor`, and upgraded color-picker behavior have been build-verified but still need manual visual confirmation in the running UI.
- `CFTextBox` validation currently uses a direct red foreground override for invalid text, so final visual approval should confirm that this matches the intended theme.
- Descriptions are still saved as a single canonical markdown line even if entered over multiple lines in the UI.
- No drag/drop reordering or search/filtering yet.

## Workarounds
- Close the running app or other locking process before rebuilding the full debug solution.
- Use `dotnet build "AgenticColorCreator.App\AgenticColorCreator.App.csproj" -c Release` when the debug solution build is blocked by the locked core DLL.
- Use the `UI Preview` tab to manually confirm delayed commit timing, float decimal-place limits, step-size behavior, arrow-key stepping, `CFColor` transparency preview, and invalid-text red feedback for `CFTextBox`, `CFInt`, `CFFloat`, and `CFColor`.
- Use category expanders to manage larger color sets until search/filtering exists.
